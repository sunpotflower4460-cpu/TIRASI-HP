# TIRASI-HP v2 第2次設計監査・実装契約

状態: REQUIRED DESIGN CORRECTIONS — 設計上の不備を補う規範文書 / 2026-10-09  
対象: main の v2総合設計 / 長期自走プレイブック / アプリの現行mainコード  
位置付け: 既存要件を削らずに明確化する **補足契約**。マスター仕様の一般表現と本書の具体的な受入条件が衝突する場合は本書のより具体的な契約を優先する。既存v1の実装事実はリポジトリ上のソースを優先する。

## 0. 再監査での中心判断

v2は「イベントHPに色テーマを追加」では終わらない。「自由にチラシを作る」「手持ちのチラシをレトロ加工する」「イベントHPを安全に維持する」の3つは共通する基盤を持つが、同じデータ型・編集経路として一体化させると破綻しやすい。最初に**制作物（Document）とイベント（Event）を分離**し、出力互換・アセット・保存復元の契約を先に確定する。

この監査の区別:
- **現行コードで確認**: 直接確認したコード上の動作/構造の記述。
- **設計上の欠落/衝突**: 現在の文書では実装判断が一意に定まらない箇所。
- **外部仕様**: 公式Web API/ライブラリ文書で明示される制約。
- **実機未検証**: 新たなE2E/印刷/PNG実行試験はこの設計監査では行っていない。

## 1. 必須補正項目（DA-01〜DA-17）

### DA-01 [P0] 3種類の制作物を独立定義する — 設計不足

旧型 EventData には Open Mic、schedule、performers 等が常設されている。20のレイアウトを追加するだけでは、ショップ告知・作品展・ワークショップ・メニュー案内・写真ポスターなどにとって不要な項目が残る。

**契約:**
- \`Event\` はイベントの事実/公開サイト用データを表す。v1からの移行対象。
- \`CreativeDocument\` は編集・書き出しできる制作物で、判別可能な \`kind\` を持つ。
- \`kind="event-flyer"\`: Eventを参照し、日付、価格、時刻、出演者、会場などのセクションを選んで表示できる。
- \`kind="free-flyer"\`: イベントを持たなくても画像、見出し、本文、日時、料金、問い合わせ、QR等の任意ブロックを構成できる。固定のOpen Mic必須を廃止。
- \`kind="image-treatment"\`: 既存画像と非破壊加工パラメータを保持する。元画像のビット列への参照を残し、イベントデータを必須としない。
- \`CreativeDocument\` は \`schemaVersion\`, \`id\`, \`name\`, \`kind\`, \`content\`, \`design\`, \`assetRefs\`, \`updatedAt\` を持つ概念型。
- 最初の実装では「空白から完全自由なベクター編集」を約束しない。free-flyerは可動ブロック/テンプレート編集から始め、レイヤー単位の自由配置は明示的な別能力として扱う。
- 既存イベントHPはEventを表示し、CreativeDocumentを勝手に公開しない。
- 編集データが何もない状態でも最小限の新規free-flyerを制作・保存・PNG出力できる。

**受入:** schedule/venue/openMicなしの自由制作チラシを作り、保存→再読込→出力できる。イベント用から自由制作へ切替えても元Eventのフィールドが消えない。

### DA-02 [P0] 「デザイン変更が本文を壊さない」を具体化 — 設計不足

- \`Event\` → \`Document\` の参照は \`eventId\` と反映方法 \`contentBinding: linked | snapshot\` を持つ。linkedはEvent変更時に文書へ反映、snapshotは編集時点で固定。勝手な上書きを防ぐためUIで選択を明示。
- タイトルを含むユーザー編集値と、テンプレートの推奨初期値を区別。プリセット変更時に既存の入力を削除しない。
- \`visibility\` と \`layoutPlacement\` は分離する。非表示にしたセクションの**データは保持**する。
- ユーザー上書きテキストとEvent由来文字列がある場合はデータソースと衝突時の優先順位をUI/型に明記。
- \`undo/redo\` は編集セッション内の本文・デザイン操作に提供し、保存状態と独立させる。破壊操作の前は確認と復旧可能な直近snapshot。

**受入:** テンプレートを10回切替えても任意ブロック、画像参照、セクション非表示、独自テキストが保持され、Undoで戻る。

### DA-03 [P0] public/draft/preview のルーティングを定義 — 設計不足

現行App.tsxでは \`/editor\` から \`/flyer\` へ遷移し、どちらも同じlocalStorageのactiveEventを利用する。v2仕様は \`/flyer\` を公開データだけに変更するため、そのままだと「編集中のチラシを見る」ボタンが意図しない公開版を表示する。

**契約:**
- \`/\`, \`/flyer\`: publishedEventのみ、閲覧者のlocalStorageに依存しない。
- \`/editor\`: local workspaceを編集。
- \`/studio\`: ローカルCreativeDocumentを編集（ローカル導線・明確なラベル）。
- \`/preview/:documentId\` 等: draftの明示的なプレビュー。非共有リンク（同一ブラウザでのみ有効）であり、公開URLと誤認させない。
- 編集から「A4を見る」はdraft previewを開き、「公開版を見る」はpublished側へ行く。クリックした先のモードを必ず画面に表示。
- \`pushState\`/戻る/進む/リロード/直URL/不明なdocumentId をE2E検証。URLだけ知っていても別端末でdraftを読めないことを説明。
- クライアントの簡易パスコードを真正な認証として扱わない。プレビューURLへの秘匿アクセス保護も保証しない。

**受入:** draftを変更しても他端末からの公開HPは同一、draftプレビューでは新しい値、ブラウザ戻るでもモードが混ざらない。

### DA-04 [P0] 旧データの「完全移行」と整合性 — 未定義

\`v1 EventData\` の保存keyは3種類（event-data, event-library, active-event-id）。新規Event/Document/Assetと複数ストアを扱う以上、型変換だけでは事故を防げない。

**契約:**
- unknown→strict parse→version detect→staged migration→参照整合性検証→commit。旧ストレージは移行成功・検証完了まで消さない。
- 既知v1フィールドは厳密に保持。未知拡張フィールドの**無損失保証はできない**ため、元JSONのバックアップを丸ごと保持し、未知値を保持するextension領域を設けるか非対応項目をユーザーへ通知。
- Event/Document/AssetのIDは一意、参照先不在はplaceholderとして検出、ID衝突は deterministic に再割当てして参照も同時更新。
- 移行は冪等。失敗/更新中リロード/ブラウザ容量不足で元データが残る。rollback経路を用意。
- old JSON import は内容プレビューと差分・件数を表示してから決定。merge/replaceは区別。
- \`schemaVersion\` はJSON単体、Library、Asset manifest各々の対象を定義（適当に全て一つにしない）。
- 移行済みとバックアップが同時に存在したときの優先順位・警告を明記。

**受入:** v1単体/複数/異常/中断復旧を繰返してデータ消失なし。元の旧JSONをいつでもバックアップ可能。

### DA-05 [P0] ローカル保存の永続性を過大表現しない — 外部仕様・設計不足

IndexedDB等のWebストレージはユーザー削除、プライベートモード、容量不足、ブラウザの退避/削除対象となり得る（MDN Storage quotas/IndexedDB）。「自動保存」だけでは安全な保存ではない。

**契約:**
- 保存成功=書き込み完了を確認した状態。メモリ上のReact state更新では成功にしない。
- \`navigator.storage.estimate()\`を可能なら補助診断に使用し、容量は推定値だと明記。重要なローカル制作データには \`persist()\` を検討するが許可不可・未対応時も動かす。
- 最低限「最近保存」「未保存」「バックアップ未取得」を区別。自動保存失敗なら明示。
- 文書+アセット同梱の**ポータブル完全バックアップ**を提供（versioned manifest + JSON +元画像/加工設定、整合性チェック）。JSONだけの書き出しは素材欠落を警告。
- インポート時はZip展開によるサイズ過大/ファイル名トラバーサル/型偽装/zip bombを防ぎ、上限・対象パスを厳しく制約。ライブラリ採用時はライセンス・更新を確認。
- originalAssetとderivedPreviewを別管理。原本はユーザーの明示削除以外で勝手に潰さない。エクスポート素材にEXIF等の位置メタデータが含まれる可能性は注意喚起。
- 全滅防止のため、バックアップ復元テストを実施して初めて「完全バックアップ可能」と判定する。

### DA-06 [P0] PNG・プレビュー・印刷は「同じDOMなら一致」ではない — 外部仕様

現行の \`html2canvas\` はCSSを完全にはサポートしない。公式ドキュメントでは filter、mix-blend-mode、object-fit、writing-mode 等が非対応として示される。したがって80s加工（粒子/ぼかし/版ズレ/混合モード）をCSSだけで実現すると、画面では見えてもPNGから消える場合がある。

**契約:**
- 共通なのは**レンダリング仕様と入力**であり、常に同一DOM/HTML実装を要求しない。画面DOM、画面Canvas、PNG用Canvas、CSS print等のadapterを認める。
- 各効果ごとに \`capabilityMatrix\` を用意（screen, png, print; tested/approximation/unsupported）。unsupportedならUIで無効化または代替を使う。
- 重要な80s質感（色調、網点、版ずれ、粒子、日付スタンプ）はCanvas 2Dや事前処理済みbitmap等で画面とPNGを共通にし、印刷への転用もテストする。
- export前にフォント・アセットロードを待ち、タイムアウト/読み込めない画像/Canvas taint/メモリ不足を区別。
- フォント/効果/画像の準備に失敗した状態で「書き出し成功」と偽らない。利用者に除外した要素を説明。
- ライブラリの選定は実験後とし、既存\`html2canvas\`を必須の最終解とはしない。より再現性の高いローカルrendererへ切り替えてよい。

**受入:** 80s効果6種をscreen/PNGで比較し、同一パラメータに対し視覚的に妥当な差（重要要素の欠落なし）がある。

### DA-07 [P0] サイズ/密度/印刷の厳密な契約 — 設計不足

- モード: \`printA4Portrait(210×297mm)\`, \`socialPortrait(1080×1350px)\`, \`socialSquare(1080×1080px)\`, \`story(1080×1920px)\`。
- A4をPNGにする場合、300dpi指定なら **2480×3508px** を目標とする（四捨五入・実際の解像度を表示）。必要に応じ150dpi軽量版を用意。ユーザー選択の解像度をファイル情報で明示。
- CSS表示寸法と物理印刷寸法と出力PNG寸法を別概念として管理。スマホのCSS拡大/縮小を保存pxの倍率に混ぜない。
- Social系はPNG必須。A4はPNGとbrowser print/PDF必須。SNS用にA4のwindow.printを呼んで「そのサイズのPDF完成」としない。
- \`window.print()\` はOS/ブラウザの印刷・PDF保存画面であり、アプリ独自の確定PDF生成ではない。UIは「印刷/PDFとして保存（ブラウザ機能）」とする。
- 紙面の背景色は \`print-color-adjust:exact\` を指定しても印刷設定による変更があり得る。完全一致を宣言せず、見本と印刷時の設定ガイドを出す（MDN）。
- bleedとsafeAreaとtrimを別定義し、家庭用余白あり/業者入稿用（要条件確認）を混同しない。
- browser canvas最大サイズ/メモリ容量を踏まえ、出力前に概算解像度とメモリ見積りを確認。大画像は軽量版/分割処理/失敗時の再試行。
- A4で内容が過剰なら密度切替/分割提案。「重要な日時・会場・料金」を非表示にして収めるのは禁止（ユーザーの明示解除を除く）。

### DA-08 [P0] 文字の溢れ・情報優先度を「警告だけ」にしない — 設計不足

- セクション属性: \`required\`, \`recommended\`, \`optional\`。イベントの意味を変える必須情報の欠落はblocking error（ただし一般free-flyerは内容に応じ必須項目を変える）。
- 溢れ計測はDOM矩形・scrollサイズ・SafeArea・改行・フォント・画像読み込み後の実測を併用。CSS overflow:hiddenや小さすぎる文字で隠さない。
- レイアウトアルゴリズムは \`layout variant → section priority → column reflow → spacing adjustment → alternate page\` の順で対応。文字の自動縮小には最小fontSizeを守る。
- 何を削ったか/二ページ目に送ったかをユーザーが見られるようにする。
- QR、日時、料金、会場、URLの読めなさを個別診断。QRは実際のURLと復号テストで検証。
- 必須情報が収まらなければ「完成PNG」とせず、編集に戻る導線と具体的な修正案を表示。

### DA-09 [P1] 20種類は「レイアウトと用途が異なる」ことが条件 — 合否の曖昧さ

- テンプレートは一枚絵としての美しさに加え、可読性/情報優先度/画像なし耐性/日本語の句読点・改行品質を持つ。
- 20個の\`templateId\`と説明文では完成条件を満たさない。各々の固有\`compositionSignature\`（大見出し領域、予定欄、主画像、重要情報配置、装飾）と代表スクリーンショットを記録。
- 20×4サイズは単純伸縮ではなく、サイズごとの\`responsiveRecipe\`が存在すること。サイズによって補助セクションを簡略化する場合は通知と元データ維持。
- 情報量が多いケースで全デザインが同じ程度に収まるとは限らない。各テンプレートは入力上限/推奨用途/失敗時のalternativesを表示する。
- 配色12個はすべてアクセシビリティ評価対象。文字/背景の基準コントラストは通常4.5:1、大文字3:1を原則（WCAG AA）。装飾テキストを含む絵柄とは扱いを区別。
- 不適切な組合せは「使用不可」または「警告付き」で選択可能範囲を明確化し、できるように見せるだけの壊れた選択肢を放置しない。

### DA-10 [P1] 時刻・曜日・タイムスケジュールの正規化 — 設計不足

- 開催日は \`YYYY-MM-DD\` のローカル日付、開始時刻は \`HH:mm\`、イベントtimezoneはIANA表記（既定Asia/Tokyo）。
- 2026.5/9形式は表示用の形式選択として保持する。v1の \`date\`,\`day\`文字列は原本を保存した上で、日付パーサが解釈できなければ入力補正を求める。
- 曜日は日付・timezoneから導出し、手動overrideは「特殊表示」として明示（矛盾警告）。
- 演目の時間表示は元の\`time\`文字列と、解釈可能なstart/endを両方管理。変換不能な曖昧な書式を削除しない。
- 重複や時刻逆転、終了より後のイベント、夜間跨ぎを自動検知するが、意図的なスケジュールを勝手に並び替えない。

### DA-11 [P1] フィルター加工の品質と範囲を固定 — 設計不足

- \`image-treatment\` は元画像に効果を加える**非生成・非破壊**機能。写真内の人物・絵を意味理解して1985年風に描き直すものではない。
- 「元テキストの保持」= 文字の形や位置を意図的に別物へ置き換えないこと。強い網点・粒子は小さな文字を読みにくくし得るため、強度上限と比較警告を表示し、原本をいつでも戻せる。
- フィルタ順序（crop → 色調 → 網点/版ずれ → 傷/粒子 → 日付スタンプ等）と座標系を明記。同一入力・同一seed・同一設定は再現可能な出力を生成する。
- 「フィルムの日付スタンプ」は撮影日データではなく演出。明示的にONにし、日付と配置をユーザーが指定。
- 破損/HEIC等未対応形式/極端な縦横比/メモリ不足で元画像を失わない。HEIC変換が必要ならアプリが実際にサポートするときだけ対応と表示。

### DA-12 [P1] アセットのリンク切れ・写真特有の問題 — 設計不足

- 保存構造: \`originalAsset\`, optional \`renderCache\`, \`previewThumbnail\`, \`contentHash\`, refCountまたは到達可能性管理。キャッシュは再生成可能、原本は保護。
- ネットURL画像は表示できてもPNGへ書き出せるとは限らない。CORS不許可なら明示的に案内し、端末アップロードへ切り替える導線。外部プロキシを勝手に設置しない。
- EXIF向きの解釈、画像クロップの永続性、フォント準備、透過PNG、URL解放、ImageBitmap close、Decode失敗の検証。
- ファイル拡張子やMIMEのみを過信せず、実デコードによって画像か判定。サイズ上限は端末の実測で決める。
- 元画像が欠損した再編集ファイルは「部分復元」であることを明示。

### DA-13 [P1] スタジオUX: 迷わない導線 + 誤操作回復 — 設計不足

- 初期画面の主動線は「イベントチラシを作る」「自由なチラシを作る」「既存画像を加工する」。非技術ユーザーが3秒でどれを選ぶかわかる文言。
- 20テンプレートは年代/用途/情報密度/写真優先等で絞れるサムネイル一覧。選択した状態がプレビューで即時変化。
- まず簡単モード（テンプレ選択、画像、本文、保存、書き出し）を見せ、詳細位置調整は折りたたみ。複数段階の調整へ押し付けない。
- 変更前後比較、編集前保存、復元、取り消し、保存状態、欠け警告がUIの中心。機能が多いだけの編集迷路を避ける。
- 80sは「時代」「媒体」「新品/経年」「色」「印刷の荒さ」を独立調整。どのテンプレも単に同じフィルターになるのを防ぐ。
- URL/QR/出演者/料金などの重要データの導線を明示。

### DA-14 [P1] 公式仕様のある外部制約をCI契約に追加

- **html2canvas**: DOMを再構成する描画であり実ブラウザ画面の完全スクリーンショットではない。CSS非対応プロパティを設計時に検査。公式: https://html2canvas.github.io/html2canvas/documentation/ / https://html2canvas.hertzen.com/features/
- **CORS canvas**: クロスオリジン画像でcanvasが汚染されるとtoBlob等がSecurityError。公式: https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image
- **Web Share**: HTTPSとユーザー操作での一時的activationが必要で、ファイル共有可否はブラウザ依存。公式: https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API
- **local persistence**: IndexedDB等は容量や削除の影響を受ける。公式: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria
- **オフライン境界**: 現行 src/styles/global.css は Google Fonts の外部URLを @import している。『データがブラウザローカル』と『ネットワーク無しで全機能が使える』は別の主張。フォント取得失敗の代替描画を必須とし、完全オフラインを表示するなら、許諾済みフォント/素材をローカル同梱してオフライン実測を行う。リモートの出演者画像URLもネットワークアクセスすることを説明する。
- **print colors**: \`print-color-adjust:exact\` はユーザー/ブラウザの印刷設定を強制しない。公式: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/print-color-adjust
- **Vite HTML metadata**: Vite \`transformIndexHtml\`などでビルド時のメタ生成は実現できるが、クライアント編集中のSEO/OGPは更新されない。公式: https://vite.dev/guide/api-plugin
- **text contrast**: WCAG 2.2 AA の一般本文4.5:1、大文字3:1。公式: https://www.w3.org/TR/wcag/

上記は製品に書く「対応済み保証」ではなく、実装時に各利用環境で実測するべき制約。

### DA-15 [P1] テスト規模と合否を現実的に整理 — 設計不足

- フェーズ内ループ: 対象moduleのunit/型/低コストsmoke。毎コミットの480画像キャプチャ等を必須にせず、作業停止を防ぐ。
- PR-A終了ゲート: v1migration往復、公開/draft分離、無効JSON、A4/PNG/print、SEO整合、ブラウザsmoke。
- PR-B日次ゲート: 新規テンプレートを追加したら、対応4サイズの代表fixtureで画像比較とoverflow測定。
- PR-B最終ゲート: 20テンプレート×4サイズ=**80基本組合せを最低1回ずつ検査**。さらに長文/画像あり/画像なし/出演者多数などの境界fixtureをrisk-basedに適用。
- 重大変更・リリース候補では必要に応じ20×4×全fixtureを実行（定常commitでは重すぎる場合）。スキップ/未実行を成功へ置き換えない。
- 目視前提の美的評価と機械検証（欠け/寸法/テキスト）が別のゲート。AIが美的品質の最終承認を自己認定しない。
- 画像差分はOS/フォント環境に依存するため基準画像のバージョンと実行環境を固定し、閾値変更は根拠を記録。
- 途中でテストが失敗したら関係する範囲を修正し、後続作業の独立性がある場合は進める。完了報告で未合格を隠さない。

### DA-16 [P1] イベント公開データとSEOの制限を明示 — 設計不足

- サイト公開元はバージョン管理された\`publishedEvent\`。ビルド時 \`index.html\` の title/OGP/JSON-LDと \`og-image\` をそれに合わせて生成。
- 静的サイトでURL単位に複数イベントを公開するならルーティング/個別metaの追加設計が必要。今回は**公開イベント1件**を基本とし、ローカルイベント一覧をすべて公開すると誤認させない。
- 公開前検証: 曜日、日時、会場、価格、SNS、初期データ、検索エンジン用情報。最新イベントへ自動で切替えたり、過去イベントを勝手に消さない。
- ストレージ内の下書きが「公開されているように見える」問題を防ぎ、公開ステータスをPR/デプロイ操作と関連付ける。
- READMEとUIは「このブラウザに保存」と「公開サイトに反映」を区別する。

### DA-17 [P0] Haiku長期自走の中断/成果管理とスコープ過多 — 設計不足

- 最終ゴールは維持: 20独立レイアウト、12パレット、4サイズ、6種類の非破壊加工、保存/出力、既存HPの安定化。
- **PR数は原則2**。作業の区切りはPRではなく内部工程とコミット/進捗ledger。PR-Aの完了待ちでPR-Bを中断しない（stacked PR利用）。
- Haikuは設計不備を見つけた時、実装に都合よく要件を削らない。進捗ファイルに \`decision needed\` と影響を記し、独立作業を続ける。
- 「20種完成」とするには可視UI・全出力サイズ・品質ゲートの証拠が必要。見た目だけ、1サイズだけ、placeholderだけはpartial。
- 作業中の設計差分は \`docs/decisions/\` 内のADRまたは進捗に理由・代替案・破棄した案を記録。マスター仕様と衝突する変更はレビュー対象。
- 中断前にブランチ/コミット/工程/テスト結果/次3手を必ず記録。コンテキスト回復後は実ファイルで裏付け。
- **「実装が可能」と「完成を実測した」を分離**。実装着手は明示依頼後。自動マージ・本番デプロイは禁止。

## 4. 監査後の残る判断と明示的な限界

決めていないことは「実装完了」としない。
- 真の管理者認証・外部共同編集・クラウド同期は今回の範囲外。
- リモート生成AIで絵柄/人物を作り直すimage-to-imageは範囲外。今回の80年代加工は非生成フィルター。
- デザインの最終的な好み、印刷実物の紙色/余白、許諾のある写真/ロゴは必要に応じ人間による最終確認。
- 20×4出力と6つの効果の一部が特定ブラウザで不可能な場合は、互換アダプター/制限/代替出力を実測で判断。無言の機能削減をしない。
- ローカルデータの保存容量/永続性は機種・ブラウザ・設定次第。完全な復旧を保証するのではなく、可搬バックアップと復元試験を提供。
