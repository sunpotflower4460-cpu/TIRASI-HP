## 1. 自走の基本動作ループ

毎回以下のループを繰り返す。

- RECONCILE: git status, git branch, git fetch --prune, git rev-parse HEAD, 最新main/PR状態を確認。対象外のユーザー変更を消さない。
- READ: 進捗ファイルの次タスク、設計の該当節、関連ソースを読む。証拠と推測を分ける。
- PLAN: 今回のコミットで満たすテスト・成果物・依存を整理。大規模でも整合性ある一塊で進める。
- IMPLEMENT: 最小限の依存追加とモジュール分割。旧動作を壊さず移行経路を作る。
- TEST: 変更に対してunit/integration/ブラウザ表示/PNG/印刷をできる範囲で実測し、できない検証は明記。
- REVIEW: 型、URL、安全性、編集の保存失敗、レイアウト寸法、モバイル操作を自分で再監査。
- CHECKPOINT: 進捗ファイルに成果/検証/失敗/次回着手点を追記。関係するソース＋進捗ファイルをコミット。
- CONTINUE: 未完成で安全な次作業がある限り、自走を続ける。質問は許可・仕様判断が本当に必要な場合に限定。

コンテキスト切れ・モデル切替・CLI停止を想定するため、メモリや会話のみに次タスクを残さない。必ずリポジトリ内に次の着手点を残す。

## 2. GitとPRのルール

- 初回実装開始時、main最新から長期ブランチ feature/tirasi-v2-reliability を作る。原則このブランチ上でPR-Aのすべてを実装する。
- PR-Aはテスト・出力検証が揃ったら1本のPRとして起票し、レビュー待ちにする。自動マージしない。
- PR-BはPR-Aがmainに反映された後、main最新から feature/tirasi-v2-flyer-studio を作るのを原則とする。PR-Aが未マージでも事前の安全な独立作業（モックやテスト設計）はできるが、本体の統合はPR-Aの最新差分を取り込んでから行う。
- どうしてもPR-Aのレビュー中にPR-B本体を進める場合はPR-BをPR-A基点でstackし、マージ前にbaseをmainへ付け替える。二重差分・衝突がないか必ず検証。
- PR数は原則2本。細かなタイポ位置・CSS微修正・1テンプレートずつを別PRに分けない。
- ただしコミットは論理的に小さくしてよい（後戻り・bisect・検証を容易にする）。強制push・履歴改変は自分の作業枝であっても無闇に行わない。
- git reset --hard、git clean -fd、force push、対象外の変更の削除は原則禁止。
- CIが失敗したら原因とテスト結果を記録し、同じブランチで修正を継続。赤いままレビュー完成としない。
- 公開デプロイは手動であるという過去PR方針がある。配信プラットフォームが確定するまで自動化しない。

## 3. PR-A内部の工程（ひとつの大きなPRのまま）

A0. ベースライン: 現行画面/PNG/A4プレビューのスクリーンショット採取、既知データのバックアップ、既存ビルド実測。ブラウザが使えない場合は「未実施」と記録。
A1. スキーマ: unknown→validate→migrate→typed EventWorkspace。legacy保存値の扱いをテストで固定。破損/半端なJSONによるクラッシュを防ぐ。
A2. 保存: localStorageの読み書き失敗時UI、イベント移動・複製・削除・一覧復元、複数タブ競合。公開と下書きを分ける。**下書きプレビュー専用route**を定義し、編集からのA4ボタンが公開版を表示する回帰を防ぐ（DA-03）。
A3. 公開整合: 直書きの前回案内を排除、publishedEventを単一公開ソース化し、vol.6とSEO/OGP/JSON-LDの一致テストを追加。
A4. 外部リンク: http/https URLバリデーション、SNS/会場/出演者画像のフォールバック、最低限のアクセシビリティ。
A5. 出力: A4トグル反映、共通の**レイアウト仕様と出力capabilityMatrix**（DOMとCanvas実装は分離可）、文字溢れの検知、PNGの段階分離とshare/download失敗回復、既存4テーマで回帰確認。A4実寸/PNG pixelとbrowser printを区別（DA-06〜08）。
A6. 品質: lockfile導入、npm ci、単体/ブラウザスモーク、代表fixture、PR説明と検証画像。READMEと使用方法更新。

A1〜A5はコードの依存により順序変更可。ただしデータ消失リスクのある箇所は最初にテストを書く。A0が終わらないままUI全面作り直しを始めない。

PR-Aの提出条件:
- publishedとdraftの表示混同なし
- legacyデータのround-tripおよび異常値拒否
- 公開イベント情報、開始時刻、共有メタ情報一致
- 現行A4/PNG/印刷動線を保持
- 原因不明のlayout overflowなし
- npm run build、追加テスト、可能なブラウザ操作検証を通過
- 未検証事項がある場合は再現手順と環境をPRに記す

## 4. PR-B内部の工程（ひとつの大きなPRのまま）

B0. PR-Aの最新変更を取り込み、既存デザインが同じデータを表示する回帰確認。
B1. **CreativeDocumentの3種類（event-flyer, free-flyer, image-treatment）**、Eventとは独立したcontentBlocks・design・assets/参照契約（DA-01/02）、registryと型/renderer/API/デザイン保存。サイズとpaletteがレイアウト本体から独立して切り替え可能な骨格を作る。
B2. 紙面計測とrender consistency。A4で画面/PNG/印刷を同じベースにし、診断を取得できることを先に確立。
B3. 80s 4種+Information Firstの5種を先行実装。単なるCSS変数違いでないことを画像比較で確認。
B4. 残り15種をファミリー単位で作成。各テンプレートに短い仕様テスト、一覧サムネイル、代表イベントの画像。
B5. パレット12種以上、フォントセット、装飾。CSS namespaceと色コントラストを検証。
B6. PNG/JPEG/WebPアップロード、IndexedDB、画像無しフォールバック、バックアップパッケージ。加えて「既存の写真・チラシを取り込み、元の文字・構図を維持して加工するモード」を実装し、1985新品印刷/1985経年/昭和コピー機/リソ2色刷り/ネオンライブ/フィルム写真の最低6プリセットと強度調整・Before/After・PNG書き出し・再編集をテストする。外部画像CORSも適切に通知。これは20レイアウトとは別機能として数え、生成AIによるimage-to-image再描画を実装済みと誤表示しない。
B7. サイズ（A4: 210×297mmとPNG 2480×3508px@300dpi、SNS縦1080×1350px、SNS正方形1080×1080px、Story1080×1920px）と安全領域、情報密度オプション。**SNSはPNG、A4だけをbrowser印刷**の基本契約とする。追加A5/A4横は品質と工数が許す場合に実装。
B8. UI: デザインギャラリー/プレビュー/スタイル切替/詳細カスタマイズ/書き出し/スマホ操作を統合。
B9. 最低20レイアウト×4サイズ=80基本組合せと境界fixtureで自動＋目視テスト。非対応効果は検出し、画面/PNG差異を確認。ブラウザE2E、PNG寸法、完全バックアップ復元、ドキュメント・PR準備（DA-09/15）。

PR-Bの提出条件:
- UIで20個の独立したテンプレートを選べる
- 同じイベント内容でレイアウトが確実に変わる
- カラーパレット12種以上/装飾の組み合わせが成立
- **free-flyer** がschedule/Open Mic/会場未入力でも成立、画像アップロード有無で動作、保存・復元、既存画像の6種類以上の非破壊レトロ加工が元文字・構図を保持して再現できる
- A4・SNS縦・正方形・StoryのPNG/印刷可能な範囲と制限が明示される
- 最大情報量ケースで紙面外欠落を無警告に出力しない
- 過去イベントと現行公開HPが壊れない
- テスト証跡とbefore/after比較が残る

## 5. Haiku向け実装方式

- 大きなソース1ファイルにすべてを詰め込まない。type/schema, migration, storage, publication, design/registry, renderers, assets, export, diagnostics, testsに責務分割する。
- まずインターフェースと契約テストを作り、コンポーネントをその型に合わせる。複数箇所で独自EventData形式を量産しない。
- JSXのデータは純粋関数で整形。イベント文字列の直書きではなくcontentから計算する。
- 各テンプレートの共通パーツ（schedule, venue, performer cards）は再利用しつつ、構図や画面の情報優先順位はレシピで差別化する。
- 装飾はCSS/SVGベースを優先し、レンダラ非互換や印刷ブラウザ制約がある場合は軽量な代替処理を提供。
- コードレビューを自走ループ内に組み込む。毎チェックポイントで「データ破壊」「export落ち」「モバイルUI」「認可を装う表現」の4観点をチェック。
- UI文言、ボタン、進捗、失敗時の次行動を日本語で統一し、ユーザーが内容を理解しやすくする。
- 処理失敗をsuccessに言い換えない。スクリーンショット未取得なら未取得、エンドツーエンド未実行なら未実行と書く。
- 既存コードに曖昧さを見つけたら、仮説→最小再現→テスト→修正と進め、根拠のない大規模削除をしない。
- 課金/クラウドサービスは使わない。依存追加が必要な場合は理由・代替・ライセンス・bundleへの影響を記録。

docs/IMPLEMENTATION_PROGRESS.mdを次の見出しで毎チェックポイント更新すること。

- 基準main SHA / 現在ブランチ / 現在コミット
- 現在工程（A0〜A6 または B0〜B9）
- 今回確定した事実（推測と分ける）
- 完成した実装（ファイルとテスト）
- テスト結果（コマンド、pass/fail/skipped、失敗理由）
- 目視確認（画像パスまたはPR artifact、未実行なら明記）
- 既知の不具合・未検証事項
- 次の着手点（優先順、具体的なファイルと操作）
- 作業再開の最初のコマンド
- ブロッカー（権限/外部判断/未取得素材など）
- 仕様変更の決定ログ（設計逸脱がある場合）
- PR URL / レビュー待ち状況 / マージ待ち状況

進捗ファイルはPRブランチ上でコミットし、PR内で最新化。実行時に最新の実装と合わなければコード事実で照合し、誤った古い進捗を修正。完了前に一度でも「done」と書くのは避け、実装済み/テスト済み/確認待ちを明確に分ける。

## 7. 中断・回復手順

コンテキスト限界、5時間制限、ネットワーク失敗、AI CLI中断、ツール非稼働を前提とする。

1. 可能なら現在の成功した差分を安全な単位でコミット。
2. 未完の作業を「何が書けた・何がまだ」「テストが通らない具体的理由」「再開位置」として進捗へ記録。
3. 変更が未コミットなら git status の状態とファイルを記す。破壊的cleanupは禁止。
4. 再開したエージェントは必ずgit statusと進捗を確認し、既存差分を上書きせずに継続。
5. PR中にreview feedbackが来たら同じPR内で修正。別PRを量産しない。
6. ローカルの画像比較アセットは必要な再現だけをGit管理。巨大画像や秘密を無断コミットしない。
7. 原因不明のテスト失敗は無限ループしない。状況を分類・絞り込み・再現可能なログを残す。許可/外部判断が必要なら質問する。
8. 不可能な要求にぶつかったときは「代替仕様」と「未実装」を区別し、勝手に仕様達成扱いしない。
9. 一定のまとまった進捗ごとにユーザーへ短く結果を報告。ただしPR作成・マージ・デプロイの判断は分ける。
10. 手戻りが多い場合は個別CSSを足し続けず、共有レイアウト契約を再検証する。

## 10. 真に質問が必要な事項

通常は設計に基づいて安全なデフォルトで進めてよい。次のいずれかに当たる場合は止まって質問する。

- 既存公開サイトに直接影響する認証/DB/公開手順の重大変更を必要とする。
- 利用規約・著作権が不明な第三者素材を含めないと要件を実装できない。
- リポジトリへpush/branch/PR作成する権限がない、または意図しない並行変更が衝突している。
- テスト不能で重大なデータ消失リスクがある。
- 外部課金や秘密鍵が必要（今回は不要な設計に戻すことを優先）。
- PRのマージや本番デプロイの明示承認を求める段階。

上記以外の細かな実装方法、UI余白、コンポーネント分割、配色は自律判断し、後で根拠を残す。ユーザーの負担を増やさず、完成度と検証を優先する。
